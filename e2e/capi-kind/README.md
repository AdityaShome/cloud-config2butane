# CAPI + kind demo

Stands up a kind management cluster, installs Cluster API with the Docker
infrastructure provider (CAPD), and provisions a one-control-plane
one-worker workload cluster where **both** nodes are bootstrapped through
CAPI's native kubeadm+ignition path  proving a Flatcar-shaped,
ignition-formatted node can be built and joined by real Cluster API
machinery, not just asserted about.

## Scope: what this does and doesn't prove

This demo does **not** feed `cloud-config2butane`'s own Butane output
through CAPI. While researching this, we read CAPI's actual bootstrap
provider source
([`bootstrap/kubeadm/pkg/ignition/clc/clc.go`](https://github.com/kubernetes-sigs/cluster-api/blob/main/bootstrap/kubeadm/pkg/ignition/clc/clc.go))
and confirmed its `format: ignition` path is parsed exclusively by the
legacy `flatcar/container-linux-config-transpiler` targeting **Ignition
spec v2.3**  a different, older schema than the Butane (Ignition spec
v3.x) this transpiler produces. There's no raw-Ignition or Butane
passthrough anywhere in that code path, so there's no way to hand it our
tool's actual output.

So this demo proves the **infrastructure side**: that CAPI + CAPD can
build and join an ignition-formatted node at all, using CAPI's own native
CLC config (an `additionalConfig` snippet that writes a marker file,
verified below). That `cloud-config2butane`'s own generated Butane is
itself correct, real, working Ignition input is what
[`../qemu/`](../qemu/) proves  against a real Flatcar Ignition consumer,
end to end.

## Prerequisites

- `docker`, `kind`, `kubectl`, `clusterctl`, `envsubst`, `curl`
- Network access (pulls `kindest/node` images on first run)
- **`fs.inotify.max_user_instances` raised above the Linux default of
  128.** kind + CAPD is containers-inside-containers, and the default
  limit gets exhausted fast  we hit it ourselves, with `kube-proxy`
  crash-looping on `too many open files` until this was raised:
  ```sh
  sudo sysctl fs.inotify.max_user_instances=8192 fs.inotify.max_user_watches=524288
  ```
- A meaningful amount of free memory  this runs two nested Kubernetes
  clusters' worth of containers (kind's own management-cluster node, plus
  CAPD's control-plane, worker, and load-balancer containers) at once.

## Run it

```sh
./run-demo.sh
```

Creates a kind cluster (`capi-mgmt` by default) with the Docker socket
mounted in (CAPD needs this to create sibling containers), installs CAPI
with `EXP_KUBEADM_BOOTSTRAP_FORMAT_IGNITION=true`, renders and applies the
workload cluster manifest from `manifests/`, waits for the control plane
to initialize, installs kindnet so the nodes can go `Ready`, and asserts:

- both the control-plane and worker nodes register and reach `Ready`
- the worker's container actually has `/opt/capi-ignition-marker`, the
  file written via `additionalConfig`  proof the ignition/CLC path
  really executed, not a silent fallback to cloud-init

Everything is torn down on exit (cluster deleted first so CAPD cleans up
its own containers, then the kind cluster) regardless of pass/fail. Set
`KEEP_CLUSTER=1` to skip teardown and leave the cluster up for inspection;
the workload kubeconfig path is printed when you do.

## Manifest provenance

`manifests/bases/` and `manifests/ignition/ignition.yaml` are vendored
from `kubernetes-sigs/cluster-api`'s own e2e test data at the exact tag
matching the `clusterctl`/provider version this demo installs
(`test/e2e/data/infrastructure-docker/main/`, tag `v1.13.4`), with the
`additionalConfig` marker content changed to something this demo can
assert on. `manifests/cni/kindnet.yaml` is vendored the same way, from
`test/e2e/data/cni/kindnet/kindnet.yaml`  CAPD's usual
`ClusterResourceSet`-based CNI installation needs a `ConfigMap` shape
that's normally generated by the upstream e2e test harness itself, so
this demo applies kindnet directly instead, which is simpler and just as
real.
